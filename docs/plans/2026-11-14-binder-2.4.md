# Binder 2.4 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Binder finds a newer GitHub release by itself and installs it from a Binder panel at the top of Settings.

**Architecture:** Tauri's updater plugin does the check, the download, the signature check and the swap, called from three Rust commands in a new `updates.rs`. The interface reaches them through the `Api` interface; the store holds the update state, so the sidebar dot and the Settings panel read the same thing, and the check at start runs there. `make release` signs a tarball of the same ad hoc signed app that goes into the DMG and writes `latest.json` with a small Node script.

**Tech Stack:** Rust 2024, Tauri 2.12, React 19, TypeScript, Tailwind 4, Vitest, Node 26 (runs `.ts` directly). New: `tauri-plugin-updater = "2"` (app).

**Spec:** `docs/specs/2026-11-14-binder-2.4-design.md`

## Global Constraints

- Repo text in English; copy plain, no exclamation marks, no em dashes, no filler. UI copy is exactly the spec's.
- The private update key lives only in the Keychain: service `io.github.kungie.binder.updater`, account `release`. Never print it, copy it into a file in the repo, or commit it. Only the public key goes in `tauri.conf.json`. Leave `io.github.kungie.binder.update-signing` untouched.
- Endpoint: `https://github.com/Kungie/binder/releases/latest/download/latest.json`. Download URL: `https://github.com/Kungie/binder/releases/download/v<version>/Binder.app.tar.gz`. Platform key: `darwin-aarch64` only.
- No updates in debug builds (`cfg!(debug_assertions)`).
- Build and test only through `make test` and `make build`. Don't run `make install`. Publishing a release needs the owner's yes, as a push does.

## Review Focus

1. Offline or GitHub down when Binder opens: no error, no dot, the panel stays as if nothing was checked. (Task 3: `a failed check at start shows nothing`.)
2. **Install and restart** while a Cloud copy runs: the button is disabled with the spec's line, and Rust refuses too if it's called anyway. (Task 2: `running_counts_transfers_in_flight`; Task 4: `install waits for a cloud transfer`.)
3. The download or the signature check fails: the running app stays, the error line shows, the button comes back. (Task 4: `a failed install shows the message and the button again`.)
4. Release notes with Markdown (headings, bullets, links, bold) or many lines: shown as plain text, at most 6 lines. (Task 4: `plainText` tests.)
5. `make release` without `build/notes.md` or without the key in the Keychain: it stops before building and prints no key. (Task 5, Step 6.)

- [ ] **Step 2: Run them.** Run: `make test`. Expected: FAIL, `running` and `updates` not defined.
- [ ] **Step 3: Implement** `running`, `percent`, the types and the three commands. `update_install`: if `state.transfers.running() > 0` return `Err("Wait for the Cloud transfer to finish.")`; check again with `app.updater()?.check()`, `Err("No update.")` when none; `download_and_install` sends `Downloading { percent }` per chunk from the running total and `Installing` when the download ends; then `state.terminals.close_all()` and `app.restart()`. Errors become their `to_string()`.

### Task 3: The update state, the start check and the sidebar dot

**Files:**
- Modify: `app/src/lib/types.ts`, `app/src/lib/api.ts`, `app/src/lib/memory.ts`, `app/src/lib/store.tsx`, `app/src/components/Sidebar.tsx`
- Test: `app/src/lib/updates.test.tsx` (new)

**Interfaces:**
- Consumes: Task 2's commands `app_info`, `update_check`, `update_install` (progress over a `Channel`).
- Produces, TS:
  - `AppInfo { version: string; updates: boolean }`, `UpdateInfo { version: string; notes: string }`, `InstallProgress = { kind: "downloading"; percent: number | null } | { kind: "installing" }`.
  - `Api.appInfo(): Promise<AppInfo>`, `Api.checkUpdate(): Promise<UpdateInfo | null>`, `Api.installUpdate(onProgress: (p: InstallProgress) => void): Promise<void>`.
  - `MemoryOptions.update?: UpdateInfo | null` (default null), `updateFail?: "check" | "install"`, `dev?: boolean`. The fake's version is `2.4.0`. Its `installUpdate` sends `{downloading, 42}`, `{downloading, 100}`, `{installing}`, then resolves and sets `installed = true` (exposed), or rejects for `"install"`. It gains `emitTransfer(t: Transfer): void` if it has no way to send a transfer yet.
  - `type UpdateState = { kind: "idle" } | { kind: "checking" } | { kind: "current" } | { kind: "available"; info: UpdateInfo } | { kind: "failed" }`. `Store.app: AppInfo | null`, `Store.update: UpdateState`, `Store.checkUpdate(quiet: boolean): Promise<void>` (quiet: a failure goes back to `idle`), `Store.transferring: boolean` (any transfer seen with `state: "running"` and not yet done, cancelled or failed).
  - `StoreProvider` prop `updateDelay = 5000`: after that many ms, if `app.updates`, it calls `checkUpdate(true)` once.
  - Sidebar `Item` takes `dotLabel` and `dotTone` (`"urgent" | "online"`); Settings gets `dot` when `update.kind === "available"`, labelled `Update available`, tone online.
