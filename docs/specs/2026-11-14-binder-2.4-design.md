# Binder 2.4: updates from inside the app

Status: waiting for the owner's review. Builds on the 2.0 to 2.3 specs, which still hold wherever this one is silent. Where they disagree, this one wins.

## Why

Today every new Binder means deleting `/Applications/Binder.app` and putting a new one in its place, by hand or with `make install`. The owner wants Binder to find a new release on its own and install it from Settings.

## Goals

- A **Binder** panel at the top of Settings with the running version, **Check for updates**, and, when a newer release exists, its version, its notes and **Install and restart**.
- Binder checks once by itself shortly after it opens. A newer release puts a small dot beside Settings in the sidebar. Nothing pops up.
- Installing downloads the release, checks its signature, replaces the app in place and opens the new one. No Finder, no DMG, no Open Anyway.
- `make release` builds everything a release needs, the update files included.

## Non-goals

- Installing updates without the owner pressing the button.
- Release channels, betas, or going back to an older version.
- Intel Macs. Releases stay Apple Silicon only, as they are today.
- Notarizing the app or a Developer ID certificate.
- Publishing a release from Binder. The owner still decides when a release goes out.

## Anti-goals

- Installing anything whose signature doesn't check out against the key built into the app.
- The private signing key in the repo, in a log, on screen or in a chat.
- Ending a Cloud copy halfway because of an update.
- A failed check at start showing an error. Being offline is normal.

## Approaches considered

- (a) **Tauri's updater plugin** (`tauri-plugin-updater`). It reads a `latest.json` from the latest GitHub release, downloads a `Binder.app.tar.gz`, checks its minisign signature against a public key in `tauri.conf.json`, swaps the app and lets Binder restart itself.
- (b) Binder's own code: ask GitHub's API for the latest release, download the DMG, mount it and copy the app over.
- (c) A Settings button that runs `make install` from the repo on the Mac.

**Chosen: (a).** It is the supported way for a Tauri app, and the signature check comes with it. (b) rebuilds the same thing without the signature check. (c) only works on a Mac with the repo and a Rust toolchain, and gives the release no part in it.

An app that downloads its own update gets no quarantine mark from macOS, so the missing notarization doesn't stop it. Only the very first install from the DMG still needs Open Anyway.

## 1. Settings: the Binder panel

The first panel in Settings, titled **Binder**.

- A line with the running version in Geist Mono: `Version 2.4.0`.
- **Check for updates**, a ghost button. While it runs it reads `Checking…` and is disabled.
- After a check:
  - Up to date: `Binder is up to date.` in text-2.
  - Newer release: `Binder 2.5.0 is available.`, the release notes below it in text-2 (plain text, at most 6 lines, then cut with an ellipsis), and **Install and restart**, a primary button.
  - The check failed: `Couldn't check for updates.` in the error colour.
- While installing, the button reads `Downloading 42%`, then `Installing…`, and is disabled. Then Binder closes and opens again as the new version.
- If the download or the signature check fails: `The update couldn't be installed.` in the error colour, and the button comes back. The running app is left as it was.
- While a Cloud copy is in the transfer tray, **Install and restart** is disabled with `Wait for the Cloud transfer to finish.` beside it.
- In a development build (`make dev`) the panel shows the version and `Updates are off in development builds.`, with no button.

## 2. The check at start

- 5 seconds after the window opens, Binder checks once, the same way the button does.
- A newer release puts a 6 px dot in the online colour beside **Settings** in the sidebar, and the Settings panel already shows it.
- A failed check at start shows nothing.
- No check after that until the owner presses the button or opens Binder again.

## 3. Installing

- Before Binder restarts, it closes the Agents' local `ssh` processes, as quitting does. The tmux sessions on the server keep running.
- The download goes over HTTPS from GitHub. The file is checked against the public key in `tauri.conf.json` before anything is replaced.
- Only a version higher than the running one counts as an update.
- Binder can only replace itself where it's allowed to write. If it can't (an app run from the DMG or a folder that isn't the owner's), the error above shows.
- Because the app is signed ad hoc, macOS may ask once after an update whether Binder can use the printer's access code in the Keychain. It already asks this after `make install`.

## 4. Releases

- A new update signing key, made once with `tauri signer generate`. The private key goes into the Keychain (service `io.github.kungie.binder.updater`, account `release`) and its file is removed. Only the public key goes in the repo, in `tauri.conf.json`. The older `io.github.kungie.binder.update-signing` item from Binder 1 stays as it is, unused.
- `make release` reads the key from the Keychain into the build's environment without printing it. Next to `build/Binder.dmg` it makes:
  - `build/Binder.app.tar.gz`: the same ad hoc signed app that goes into the DMG.
  - its signature, made with the key.
  - `build/latest.json`: the version, the release notes, the date and, under `darwin-aarch64`, the signature and the download URL `https://github.com/Kungie/binder/releases/download/v<version>/Binder.app.tar.gz`.
- The release notes come from a file the release reads, `build/notes.md`, written for each release.
- The app checks `https://github.com/Kungie/binder/releases/latest/download/latest.json`.
- A release is published with `gh release create v<version>` and the three files. The owner says yes first, every time, as with a push.

## 5. The first update

Binder 2.2.0, now in `/Applications`, has no updater. 2.4.0 is installed by hand one last time. From then on, updates come from Settings.

## Left to the builder

- Whether the check and the install live in Rust commands or in the updater's JavaScript API, as long as the interface keeps talking to the `Api` interface and the in-memory fake can stand in for it in tests.
- How the release notes are cut down to plain text.
- Where in the Makefile the update files are made, and whether a small script does it.

## Calls I made (owner, please check)

- The Binder panel goes first in Settings, not last.
- The check at start waits 5 seconds and runs once.
- An update can't be installed while a Cloud copy is running.
- No updates in development builds.
- Release notes come from `build/notes.md`.
