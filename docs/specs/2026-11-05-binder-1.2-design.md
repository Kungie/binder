# Binder 1.2: search, import, forgetting, code summaries

Status: draft, waiting for review. Builds on the 1.1 spec. Ships as 1.2.0.

**Language:** everything Binder shows or writes is English, whatever language a session or an imported file is in.

## 1. Search

- `binder search <words> [--project <name>] [--all] [--limit <n>]` searches every note: decisions with their details, observed lines, the user's own text, topic notes, and kept files' captions.
  - Results come back best first. Each is `path: line`, the whole reply stays under about 1,500 characters, and secrets are redacted.
  - Superseded lines are left out unless `--all` is given.
- Ranking is keyword ranking with no model and no network: BM25 over lowercased words. Exact phrase hits rank higher, and so do lines in the current project (`--project`, or the project of the folder it runs in).
- The session card's header gains one line: `Missing something? Run "<path to binder>" search <words>.` The path is the helper's own path, so it works without `binder` on the PATH.
- A search that returns a line counts as **used** for that line and its note (section 5 of 1.1).
- The main window's search field also matches note contents, not just titles. A note that matches shows under its folder with its best line under the title.

Tests:
- Ranking puts an exact phrase first.
- The project boost puts the current project's lines first.
- Superseded lines appear only with `--all`.
- The reply stays under its size limit with 500 notes.
- Secrets are redacted.
- A search records use.
- The card header names the helper path.

## 2. Import CLAUDE.md and AGENTS.md

- **Sources:**
  - `~/.claude/CLAUDE.md` goes to me.md.
  - Each project's `CLAUDE.md`, `AGENTS.md` and `.claude/CLAUDE.md` go to that project. Projects are the ones Binder already knows, found in the project roots.
- The model, on the user's own plan and only with consent, splits each file into short English lines, the same shape as a review: kind, scope, text, detail, topic and confidence. At most 40 lines per file. Each line becomes a catch card with the evidence `from CLAUDE.md` (or the file's name). Nothing is written without Keep.
- A file is imported once per version. `.binder/imported.json` keeps each file's path and SHA-256, so a changed file is offered again and an unchanged one is not.
- **When:**
  - Right after setup, if consent is on.
  - **Import** in Settings.
  - `binder import` on the command line.
  - Without consent, Settings explains that importing needs Read sessions with your Claude plan.
- Lines Binder already has, or the user dropped before, are not offered again (the inbox's normal dedupe).

Tests:
- me and project routing.
- Unchanged files are skipped and changed ones are offered.
- The 40-line cap.
- With no consent, nothing runs.
- The prompt asks for English.
- Dedupe against kept and dropped lines.

## 3. Before Claude Code compacts

- `binder install` adds a `PreCompact` hook that runs `binder capture --now`. It catches what the session decided before compaction squeezes the transcript.
- With consent, the waiting talk is summarized at once, whatever the batch size (the same as a quiet session).
- After compaction, Claude Code's own SessionStart, `source: compact`, gets the card again, as today.

Tests:
- install and uninstall add and remove the PreCompact hook without touching others.
- `--now` claims the waiting talk regardless of the 4,000-character threshold.

## 4. Lessons from failed commands

- The transcript reader marks a Bash command whose tool result is an error. It keeps the command and the first 300 characters of the error, redacted.
- With consent, the review sees them as `FAILED: <command> · <error>` lines. It may propose a lesson such as "On hetzner-1, docker compose needs sudo." Its source is `.failure`, and the card tag reads `FROM A FAILED COMMAND`.
- Without consent, nothing is proposed from failures.

Tests:
- The reader pairs a failed tool result with its command.
- The review input lists failures.
- The failure source decodes, and its provenance is `learned from a failure`.

## 5. Forgetting and feedback

- **Fading.**
  - **Which lines fade:** a decision in a project, topic, server, machine or hosting note that is older than 90 days. It must also never have been used by an agent (section 5 of 1.1).
  - **Effect:** a faded line leaves the session card but stays in the note.
  - **Exceptions:** me.md and access notes never fade.
  - **In the main window:** faded lines show dim under `Fading · not on the card`. **Keep on card** pins a line, and pinned lines never fade. Pins live in `.binder/usage.json` by line hash.
- **Wrong.** Every decision line in the main window gets **Wrong**.
  - It moves the line to Superseded, marked `· wrong <day>`.
  - It records the line as dropped for that note, so the same text is never offered again.
  - The review is shown up to 20 recent wrong lines as `NOT TRUE:`, so it doesn't propose them in other words.
- **Expiry.**
  - The review may add `"until": "YYYY-MM-DD"` to a temporary fact, such as "the API is down until Friday".
  - Keep records the date in `.binder/expiry.json` by line hash. The note line keeps its normal format.
  - Tidy moves expired lines to Superseded, marked `· expired <day>`, and the card leaves them out from that day.
  - The main window shows `UNTIL 8 NOV` beside such a line.

Tests:
- A line older than 90 days and never used fades; a used, pinned, me or access line does not.
- Wrong supersedes, marks the line, and blocks it from coming back.
- The review input lists `NOT TRUE` lines.
- Expiry is recorded on Keep, and Tidy moves the line on the day.
- The card drops faded and expired lines.

## 6. Code summary

- **Summarize code** on a project page, and `binder index [<folder>]` on the command line, each run the model once.
- **What the model reads, on the user's plan and with consent, at most about 20,000 characters:**
  - the repo's file list from `git ls-files`, folded into folders past 300 entries;
  - the README;
  - the build and deploy files that exist: `Package.swift`, `package.json`, `Cargo.toml`, `pyproject.toml`, `go.mod`, `Gemfile`, `Makefile`, `Dockerfile`, `docker-compose.yml`, `fly.toml`, `wrangler.toml`, `vercel.json`, `netlify.toml` and `.github/workflows/*`, each cut to 3,000 characters;
  - **never** `.env` files, keys, or anything the secret filter flags.
- **What it returns:**
  - up to 15 lines about the architecture: main parts, how they talk, where things live, how it builds and deploys;
  - each line with a topic (`architecture` by default) and a detail.
- Each line is a catch card with the evidence `summarized from the code`. Keep files lines into `projects/<name>/architecture.md` or the topic the model chose.
- The project's folder is found from its git repo in the project roots, the same way the projects observer finds it. If none is found, the button says so.

Tests:
- The file list folds past the cap.
- Manifests are cut to 3,000 characters.
- `.env` and key files are never read.
- With no consent, nothing runs.
- Lines go to `architecture` by default.
- The prompt asks for English.

## Privacy

- Every new path still ends in a catch card and Keep. Search, fading, pins, expiry and the import record store only paths, hashes and dates.
- The model runs only with consent, on the user's own plan, with secrets redacted before and after.

## Not in 1.2

- An MCP server: the user chose the CLI.
- Embeddings or semantic search.
- Per-prompt injection.
- Importing `.cursorrules` or ChatGPT exports.
- Re-summarizing code automatically.
