# Binder 1.1: richer memory, files, usage

Status: draft, waiting for review. Builds on `2026-10-26-binder-v1-design.md`. Ships as 1.1.0.

Eight changes, in the order the user listed them. Each says what the person sees, what is stored, and how it is tested.

## 1. Summary or detailed catch cards

- Settings › Menu bar gets a switch **Show catches in detail**, off by default.
- Off (summary): the card shows today's one short sentence.
- On (detailed): the card also shows a 2–3 sentence explanation and its source. For a command that's the full command. For the chat, a short quote of what was said (at most 200 characters, redacted).
- The summarizer's review reply gains two optional fields per item: `"detail"` (the explanation) and `"quote"`. Command and observer proposals fill `detail` from their evidence, without a model call.
- `Proposal` gains `detail: String?` and `quote: String?`, decoded with `decodeIfPresent` so older inbox files still load.
- Keep writes the short sentence as the decision line, as now. If there is a detail, it goes on an indented line right under it: `  - <detail>`. Supersede, Restore, Tidy and the card treat a decision and its indented lines as one item. The session card leaves details out, to stay inside its budget.
- `BinderState.detailedCatches` (default `false`).

Tests: the review parser reads `detail` and `quote`, and older replies without them still parse. Keep writes the indented detail. Supersede and Restore move the detail with its line. The card never contains detail lines. State without the key decodes to `false`.

## 2. Where a catch will go

- Every card says where Keep files it, after the source tag: `→ dawn · hosting`, `→ me`, `→ hetzner-1`. The label comes from the proposal's target path, plus any extra notes from section 6 (`→ dawn · hosting + hetzner-1`).

Tests: `ProposalCard.destination(for:)` for a project note, a topic note, me.md, a server and a proposal with extra notes.

## 3. Topic notes inside a project

- A project can have topic notes at `projects/<project>/<topic>.md`, for example `projects/dawn/hosting.md`. `projects/<project>.md` stays the project's overview.
- The model picks the topic. The review reply gains `"topic"` per project item: a lowercase slug of one or two words (`hosting`, `auth`, `payments`). It is shown the project's existing topics and told to reuse one when it fits. Binder normalises the slug (lowercase, letters, digits and dashes, at most 24 characters). With no topic, the item goes to the overview as now.
- The overview gets a `[[<project>/<topic>]]` link the first time a topic note is made, so Obsidian and the graph see the connection.
- The session card shows the overview, then each topic's decisions under its name (`HOSTING:`), newest first, trimmed by the existing budget logic: oldest topic lines go first, the overview's last.
- A project note in the main window gets **Split by topic**. It asks the model once to sort the overview's existing decisions into topics and moves them. It moves only lines the model names. Nothing is deleted, and moved lines can be moved back with Edit (section 4).
- Graph: topic notes are note nodes tied to their project with a structure edge, labelled with the topic name. Wikilinks resolve `<project>/<topic>`.
- The sidebar's project count stays one per project. A project's page lists its topics under the overview.

Tests: slug normalisation; keep into a topic creates the note and the overview link once; the card groups topics and stays under budget; Split moves only named lines; the graph has topic nodes and edges.

## 4. Edit and delete in the main window

- A note's **Edit** opens an editor inside Binder instead of an external app. It edits everything outside the observed block. The observed block is shown read-only above it, because the observers rewrite it. **Save** writes the file; **Cancel** leaves it. Open in Obsidian stays as a second button.
- Each decision line gets **Delete** on hover. It removes the line, and its detail, from the file after a confirmation.
- Each note gets **Delete note**, which moves the file to the macOS Trash after a confirmation, so it can be recovered from there. me.md can't be deleted.
- A note changed on disk while the editor is open shows "Changed outside Binder" and Save asks before overwriting it.

Tests: saving keeps the observed block byte for byte; deleting a line removes only that line and its detail; Delete note uses the Trash (`FileManager.trashItem`) and refuses me.md.

## 5. What sessions used

Binder records two counts per note and per decision line in `.binder/usage.json`:

- **On cards:** how many session cards included it. `binder card` records this when it builds a card. This count is exact.
- **Used by agents:** how many times a session acted on it. Capture counts this from the transcript. A note counts as used when a command contains one of its handles (a host alias, IP or hostname, a domain, a key name, a repo), or when the agent's reply repeats one of its decision lines. This count is an estimate, and the UI says so.

Shown:

- On each note in the main window: `On 40 session cards · used 12 times · last today`.
- On each decision line on hover: `On 31 cards · used 4 times`.
- On the Graph, a node's size grows a little with use.
- Settings › About shows the totals.

Usage only ever counts. It stores no text from the transcript.

Tests: building a card increments the right notes and lines once per session (a second `card` for the same session doesn't double-count); handle matching finds `ssh hetzner-1`, `ssh root@10.0.7.20` and `wrangler pages deploy` against the right notes and ignores lookalikes; usage.json from an older version, or a missing one, loads empty.

## 6. Hosting and server facts also go to their own notes

- The review reply gains `"also"` per item: up to two extra notes it belongs in, as `server:<name>` or `hosting:<provider>`. Example: "dawn's API runs in Docker on hetzner-1" goes to the dawn note and to `servers/hetzner-1.md`.
- A new folder, `hosting/`, holds a note per provider (`hosting/cloudflare.md`, `hosting/fly.md`) for facts about the account or service rather than one machine. It appears in the sidebar and the graph like the other folders.
- Command rules do the same without a model. A `wrangler`, `fly`, `vercel` or `netlify` command also files under that provider, and `ssh <host>` facts under that server.
- On Keep, the line is written to every target. In the extra notes it ends with `· for [[<project>]]`, which also links them in the graph. Drop drops all of them. Edit before Keep edits all of them.
- `Proposal` gains `also: [String]` (vault paths), decoded with `decodeIfPresent`.

Tests: the parser maps `server:` and `hosting:` to paths and ignores anything else; Keep writes all targets once each; dedupe still works per target; a command rule files a deploy under its provider.

## 7. Your home server

A one-time change to your own binder, not to the app: a note `machines/raspberry-pi.md` for the Raspberry Pi at 192.168.0.14 (SSH, Home Assistant, HTTP), written as "written by you", linked from `servers/homelab.md`. You can rename it or fill in more with the new Edit.

In the app: when you answer **Mine** to a homelab host, it gets its own note in `machines/` instead of a line in `servers/homelab.md`.

Tests: Mine creates `machines/<name>.md`; Not mine still drops it.

## 8. Images and PDFs from sessions

- Capture finds:
  - images and PDFs you attach to a session (the transcript's `image` and `document` blocks);
  - images and PDFs the agent writes to disk during the session: `Write` tool paths, and paths in a command that exist afterwards and were modified during the session.
- Screenshots an agent takes only to look at something (images inside tool results) are skipped. A session yields at most 6 file cards, newest first. Files are deduped by SHA-256 across the inbox and the binder. Anything over 20 MB, or an image under 64 × 64 pixels, is skipped.
- Each becomes a catch card with a thumbnail, or for a PDF its name and page count. The caption is the text you sent with it, or the file name, plus the note it goes to (section 2). The card says "Check for passwords or keys before keeping".
- Waiting files live in `.binder/inbox/files/`. **Keep** moves the file to `files/<project or me>/<yyyy-mm-dd>-<name>.<ext>` and adds a decision line `![[files/…]] <caption>` to the note. **Drop** deletes the waiting copy. Nothing reaches the binder without Keep.
- The session card lists a project's kept files as paths, so an agent can open one when it needs it.
- The main window shows a note's files as thumbnails. Click opens the file in Preview.

Tests: base64 blocks are decoded to files with the right extension; tool-result images are ignored; the per-session cap, size limits and dedupe; Keep moves the file and writes the line; Drop deletes the waiting file; the card lists file paths and stays under budget.

## Privacy

- Every file and fact still goes through Keep.
- Usage stores counts only.
- The topic, detail, quote and also fields come from the summarizer, which still runs only with consent and with secrets redacted before and after.

## Not in 1.1

- Reading the content of images or PDFs with a model.
- Moving existing lines into server or hosting notes. Split by topic covers projects only.
- Usage per file.
